# StatementCore: parser extraction plan

## What exists today

All statement logic lives in `BadeKit` (one SPM package, many targets). Nothing parses in the
app target itself.

| Concern | Where | Notes |
| --- | --- | --- |
| Text extraction | `Pipeline/StatementImporter.swift` | `PDFKit`: joins `PDFPage.string` of every page. A non-PDF file is decoded as UTF-8. **Stays in the app.** |
| Parser contract | `Ingestion/StatementParser.swift` | `canParse(_:)`, `parse(_:) -> [RawTransaction]`, `exchangeRates(in:) -> [ObservedRate]` |
| Bank of Georgia | `Ingestion/BOG*.swift` | `bog-pdf-v1`. Flattens whitespace, splits on the record label, reads fields by label. |
| TBC Bank | `Ingestion/TBC*.swift` | `tbc-pdf-v1`. Recognised by the BIC `TBCBGE22`; reads the intact card block after `POS `. |
| Dates | `Ingestion/StatementDate.swift` | Fixed UTC Gregorian calendar (`Calendar.bade`). |
| Merchant cleaning | `Normalization/` | Tier 1 only: strip location tail, per-charge reference, processor prefix, domain, whitespace. |
| Merchant matching | `Catalog/` | `MerchantSeed.swift` (~450 brands, the seed file) behind `BundledCatalog`: whole-word, case/punctuation-folded token match, first entry wins. Also price-point matching and typed-name suggestions. |
| Recurring detection | `Detection/` | Pure. Dedup → MCC blocklist → group by (merchant, currency) → phase-fitted cadence → confidence → price changes, variable amounts, lapse. Repeats with no rhythm become candidates. |
| Shared models | `Core/` | `RawTransaction`, `CurrencyConversion`/`RateBook`, `ObservedRate`, `Cadence`, `DetectedSubscription`, … |

### Supported statement formats

The file picker accepts `.pdf`, `.txt` and `.csv`, but every file ends up as one string and only
two parsers exist. A CSV is read only if its text happens to look like one of these.

1. **Bank of Georgia, English export** — records open with `Payment - Amount`; fields
   `Merchant:`, `MCC:`, `Date:`; optional `Card scheme conversion rate (USD-GEL):` and
   `Bank conversion rate (USD-GEL):` lines; the holder's own conversions print as
   `Amount: USD100.00; Foreign Exchange. FX Rate:2.7. Counter-amount: GEL270.00`.
2. **Bank of Georgia, Georgian export** — the same layout with Georgian labels
   (`გადახდა - თანხა`, `ობიექტი:`, `თარიღი:`, `საბარათე სქემის`/`ბანკის კონვერტაციის კურსი`,
   `ვალუტის გაცვლითი ოპერაცია. კურსი:… კონტრთანხა:`).
3. **TBC Bank export** — bilingual header, Georgian operation labels. A card purchase is
   `POS [GEO] - MERCHANT, 8.31 GEL, Aug 11 2025 03:12PM, city, country, MCC: 5912, …`; the
   purchase moment is inside the block, the posting date in front of it. Conversions print as
   `(ყიდვა-გაყიდვა: 1 USD = 2.7100 GEL)`, sometimes per 100 units.

No other bank has a parser (a Liberty statement is deliberately claimed by neither).

### Known gaps already recorded in `CLAUDE.md`

1. BOG English exports inject `pg. N (Total N pg.)` plus a balance mid-field; `flatten` never
   strips it, so the record it lands in is lost.
2. BOG "Form B" (`Automatic conversion, rate:`) is unread in both languages.

## Plan

1. **Write this plan and commit it** → verify: file committed and pushed.
2. **Create `Packages/StatementCore`** (Foundation only, no dependencies, one library target)
   and copy, file for file and unchanged: the `Core` models the logic needs, `Ingestion`,
   `Normalization`, `Catalog` (including the seed), `Detection`, and the pipeline minus PDFKit as
   `StatementAnalyzer.analyse(text:)`. The app's files stay where they are.
   → verify: `swiftd build` passes.
3. **Port the existing unit tests** for those modules into the package, imports changed only
   → verify: `swiftd test` passes before any fixture exists, so the copy is proven faithful.
4. **Synthetic fixtures** in `Packages/StatementCore/Tests/Fixtures`: invented data only,
   `GE00TEST0000000000000`-style accounts, `000000******0000` cards, no person names, local shops
   with obviously fake names. Each fixture is `<name>.txt` (the statement as extraction delivers
   it) plus `<name>.expected.json` (hand-written expectation, never generated by running the code).
   At least 10 per format (BOG English, BOG Georgian, TBC), covering between them:
   Georgian / English / mixed descriptions; GEL, USD, EUR amounts and conversion lines; refunds and
   reversals; one merchant written several ways; recurring and one-off charges; month and year
   boundaries; thousands separators and decimal commas; empty and malformed rows; plus a few
   format-less files (empty, unrecognised).
5. **Fixture tests**: for every fixture, check which parser claims it, every transaction (date,
   description, amount, currency, MCC, conversion), the merchant each resolves to, the exchange
   rates, and the detected subscriptions and candidates. → verify: `swiftd test`.
6. **Fix what the fixtures expose in the package copy only**, one commit per bug, each with a
   test that failed before. Every bug is listed in the PR so it can be ported to `BadeKit`.
7. **Draft PR** listing changes, decisions, and the Xcode/`BadeKit` switch-over steps.

### Expected-output schema

```json
{
  "parser": "bog-pdf-v1",
  "error": null,
  "transactions": [
    {"date": "2026-05-27", "description": "GOOGLE *YouTubePremium, United States of America",
     "amount": "10.29", "currency": "GEL", "mcc": "4899", "merchant": "YouTube Premium",
     "conversion": {"from": "USD", "to": "GEL", "bankRate": "2.6716", "schemeRate": "2.6317"}}
  ],
  "rates": [{"date": "2026-03-12", "from": "USD", "to": "GEL", "rate": "2.6716"}],
  "subscriptions": [
    {"merchant": "YouTube Premium", "currency": "GEL", "cadence": "monthly", "amount": "17.49",
     "charges": 3, "confidence": "confident", "variable": false, "ended": false,
     "next": "2026-08-27", "priceChanges": [{"date": "2026-06-27", "from": "10.29", "to": "17.49"}]}
  ],
  "candidates": [{"merchant": "…", "currency": "GEL", "charges": 3}]
}
```

Amounts are strings so they stay exact `Decimal`s. Derived rates are compared to six places.

### Things to check while writing fixtures

- Synthetic shapes for refunds and reversals are a guess: no anonymised fixture contains one.
  They follow each bank's own header convention (`<Kind> - Amount` for BOG, a non-card row or a
  negative card block for TBC) and are expected never to become purchases (`RawTransaction` is
  debits only).
- BOG reads a record's fields up to the next *payment*, so a non-payment record in between can
  lend it its MCC, date or conversion lines.
- Amounts and dates are searched for rather than anchored to their label, so an unreadable one
  may be replaced by a later match.
- `Calendar.date(from:)` is lenient: `31/02/2026` may roll over instead of being rejected.
- Neither parser reads a decimal comma.
- TBC splits records on `POS ` anywhere, including inside a merchant name.
